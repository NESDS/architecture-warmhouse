### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут удалённо включать/выключать отопление в своих домах

### 2. Анализ архитектуры монолитного приложения

- **Язык программирования:** Go
- **База данных:** PostgreSQL
- **Архитектура:** Монолитная, все компоненты системы (обработка запросов, бизнес-логика, работа с данными) находятся в рамках одного приложения
- **Взаимодействие:** Синхронное, запросы обрабатываются последовательно
- **Масштабируемость:** Ограничена, так как монолит сложно масштабировать по частям

### 3. Определение доменов и границы контекстов

# Задание 2. Проектирование микросервисной архитектуры


### Основные микросервисы:

1. **Auth Service** - управление пользователями и подписками SaaS
2. **Device Service** - управление устройствами и протоколами взаимодействия
3. **Automation Service** - управление сценариями и выполнение пользовательских скриптов
4. **Telemetry Service** - сбор данных с устройств и хранение телеметрии
5. **Lighting Service** - управление системами освещения
6. **Security Service** - управление воротами, замками и видеонаблюдением
7. **Notification Service** - система уведомлений и алертов

### Взаимодействие микросервисов:

**Синхронное взаимодействие (REST API):**
- Пользователь → API Gateway → соответствующий микросервис
- Микросервисы обращаются друг к другу через API Gateway для критичных операций

**Асинхронное взаимодействие (Message Broker):**
- Device Service публикует события изменения состояния устройств
- Automation Service подписывается на события для выполнения сценариев
- Security Service публикует алерты безопасности
- Notification Service обрабатывает все уведомления

**Хранение данных:**
- Main Database (PostgreSQL) - основные данные бизнес-логики
- Telemetry Database (TimescaleDB) - временные ряды телеметрии
- Redis Cache - быстрый доступ к состояниям устройств и сессиям
- S3 Storage - видеозаписи и файлы

# Задание 4. Создание и документирование API

### 1. Тип API

**REST API** - используется для синхронного взаимодействия между микросервисами, когда требуется немедленный ответ:
- Device Service - управление устройствами (CRUD операции, команды управления)
- Telemetry Service - сбор и анализ телеметрических данных
- Automation Service - управление сценариями автоматизации
- Security Service - управление системой безопасности

**AsyncAPI** - используется для асинхронного взаимодействия через брокер сообщений:
- Notification Service - система уведомлений и алертов
- Обмен событиями между микросервисами (изменение статуса устройств, оповещения безопасности, выполнение сценариев)

**Обоснование выбора:**
- REST API подходит для операций, требующих немедленного ответа (получение данных, выполнение команд)
- AsyncAPI обеспечивает надежную доставку уведомлений и событий без блокировки основных операций
- Комбинация обеих подходов обеспечивает оптимальную производительность и отказоустойчивость системы

### 2. Документация API

**REST API документация (OpenAPI/Swagger):**

- [Device Service API](api/device-service-api.yaml) - управление устройствами умного дома
- [Telemetry Service API](api/telemetry-service-api.yaml) - сбор и анализ телеметрических данных
- [Automation Service API](api/automation-service-api.yaml) - управление сценариями автоматизации
- [Security Service API](api/security-service-api.yaml) - система безопасности и контроля доступа

**AsyncAPI документация:**

- [Notification Service AsyncAPI](api/notification-service-asyncapi.yaml) - асинхронная система уведомлений

**Ключевые эндпоинты:**

**Device Service:**
- `GET /devices` - получение списка устройств
- `POST /devices` - добавление нового устройства  
- `GET /devices/{id}` - получение информации об устройстве
- `PUT /devices/{id}` - обновление состояния устройства
- `POST /devices/{id}/command` - отправка команды устройству

**Telemetry Service:**
- `POST /telemetry/data` - отправка телеметрических данных
- `GET /telemetry/data/{deviceId}` - получение истории данных устройства
- `GET /telemetry/analytics/summary` - получение аналитических отчетов

**Automation Service:**
- `GET /scenarios` - получение списка сценариев
- `POST /scenarios` - создание нового сценария
- `PUT /scenarios/{id}` - обновление сценария
- `POST /scenarios/{id}/execute` - ручное выполнение сценария

**Security Service:**
- `GET /security/devices` - получение устройств безопасности
- `POST /security/devices/{id}/control` - управление устройством безопасности
- `GET /security/access-log` - журнал доступа
- `GET /security/alerts` - оповещения безопасности

**Notification Service (Async):**
- Каналы: `device/status`, `security/alerts`, `automation/scenario`, `telemetry/threshold`
- Поддерживает события изменения статуса устройств, оповещения безопасности, выполнение сценариев и пороговые уведомления

# Задание 5. Работа с docker и docker-compose

Перейдите в apps.

Там находится приложение-монолит для работы с датчиками температуры. В README.md описано как запустить решение.

Вам нужно:

1) сделать простое приложение temperature-api на любом удобном для вас языке программирования, которое при запросе /temperature?location= будет отдавать рандомное значение температуры.

Locations - название комнаты, sensorId - идентификатор названия комнаты

```
	// If no location is provided, use a default based on sensor ID
	if location == "" {
		switch sensorID {
		case "1":
			location = "Living Room"
		case "2":
			location = "Bedroom"
		case "3":
			location = "Kitchen"
		default:
			location = "Unknown"
		}
	}

	// If no sensor ID is provided, generate one based on location
	if sensorID == "" {
		switch location {
		case "Living Room":
			sensorID = "1"
		case "Bedroom":
			sensorID = "2"
		case "Kitchen":
			sensorID = "3"
		default:
			sensorID = "0"
		}
	}
```

2) Приложение следует упаковать в Docker и добавить в docker-compose. Порт по умолчанию должен быть 8081

3) Кроме того для smart_home приложения требуется база данных - добавьте в docker-compose файл настройки для запуска postgres с указанием скрипта инициализации ./smart_home/init.sql

Для проверки можно использовать Postman коллекцию smarthome-api.postman_collection.json и вызвать:

- Create Sensor
- Get All Sensors

Должно при каждом вызове отображаться разное значение температуры
